## 1. 요약

| 질문 | 답 |
|---|---|
| 벡터만 쓰면? | 직업의 **업무 설명**은 잘 찾지만(일반 질문 정답 근거 96.7%), **학과·핵심능력·자격 같은 관계 근거는 하나도 못 가져온다**(Multi-hop·관계비교 0%). 업무 설명 벡터에 관계 정보가 없기 때문이다 |
| 그래프를 결합하면? | 관계 근거를 가져온다. 정답 근거 재현율 Multi-hop 0.82~0.87, 관계비교 0.72~0.85 |
| 실제 시스템(Jev 라우팅 + CRAG)은? | Multi-hop **1.00**, 관계비교 **0.92**. 재검색·근거 선별이 단일 호출보다 낫다 |
| 검색 경로는 맞게 골랐나? | 138문항 중 105건(**76%**) 일치. 불일치 33건 중 30건은 Multi-hop을 `hybrid`로 기대했는데 라우터가 `graph`를 고른 것이다 |

## 2. 비교 방법

| 항목 | 내용 |
|---|---|
| 질문 | 평가셋의 일반 30 · Multi-hop 30 · 관계비교 30 (총 90문항, 정답 근거 ID가 있는 것) |
| `vector` (기준선) | `vector_search`만 직접 호출(질문을 그대로 임베딩, top 5). 그래프 단계 없음 |
| `graph` | Jev 분류를 graph로 고정하고 실제 검색 워커 실행(GPT가 Cypher 작성) |
| `hybrid` | 분류를 hybrid로 고정하고 실행(벡터 후보 → 그래프 확장) |
| `system` | 라우터가 직접 고른 방식 + CRAG 평가·재작성을 거친 최종 근거(RAGAS 실행 `ragas_20261116_crag`) |
| 지표 | `job_recall` 정답 직업이 근거에 나온 비율 · `evidence_recall` 정답 근거 ID(예 `CAREER0131:core_abilities`) 중 찾은 비율 · `hit_all` 정답 근거를 모두 찾은 질문 비율 |

| 일반 | vector | 0.967 | 0.967 | 0.967 | 5.0 | 0 |
| 일반 | graph | 0.967 | 0.100 | 0.100 | 1.1 | 0 |
| 일반 | hybrid | 0.967 | 0.933 | 0.933 | 9.3 | 1 |
| 일반 | system | 0.967 | 0.967 | 0.967 | 1.0 | 0 |
| Multi-hop | vector | 0.817 | **0.000** | 0.000 | 5.0 | 0 |
| Multi-hop | graph | 0.867 | 0.867 | 0.867 | 3.9 | 3 |
| Multi-hop | hybrid | 0.900 | 0.817 | 0.800 | 10.8 | 1 |
| Multi-hop | system | **1.000** | **1.000** | **1.000** | 5.0 | 0 |

| 관계비교 | system | 0.917 | 0.917 | 0.833 | 1.8 | 0 |

읽는 법
- **벡터 단독은 관계 질문에 구조적으로 답할 수 없다.** 정답 근거가 `core_abilities`, `related_certificates`, `related_majors` 필드인데 벡터 인덱스는 `work`(업무 설명)만 담는다. 직업은 찾아도(0.82~0.87) 질문이 요구한 관계 값은 0이다.
- **graph 단독은 관계 질문에 강하지만 일반 질문에는 쓸 수 없다**(일반 evidence_recall 0.10). 직업 설명(`work`)을 그래프 관계로 가져오지 않기 때문이다.
- **hybrid는 두 종류를 모두 가져오지만 근거가 많다**(평균 8~11개). 불필요한 근거가 섞여 답변 단계의 부담이 커진다.
- **system이 가장 좋은 이유:** 단일 호출 결과(graph, hybrid는 한 번에 끝)와 달리 CRAG가 근거를 평가해 쓸 것만 남기고, 부족하면 검색어를 고쳐 다시 찾는다(Multi-hop 8건, 관계비교 13건이 재작성). 근거 수가 1~5개로 적은 것도 이 선별 때문이다.
- **답변에 미치는 영향:** 같은 질문 "의료장비기사와 가전제품 설치 및 수리원은 공통으로 연결된 핵심능력이 있나요?"는 벡터만으로는 두 직업의 업무 설명만 나오고 "손재능"이라는 공통 능력은 나올 수 없다. 그래프를 따르면 `core_abilities` 근거(`CAREER0009:core_abilities`, `CAREER0026:core_abilities`)로 직접 답한다. 답변 품질(RAGAS)은 [통합 평가 보고서](CareerGraph_통합평가_보고서_20261116.md)에 있다.

### 주의
- 질문마다 한 번씩 실행한 결과다. graph, hybrid는 GPT가 Cypher를 쓰는 과정에서 흔들린다(오류 포함 건수는 표의 오류 열). 두 방식은 실패하면 재현율 0으로 계산했다.
- `system` 근거는 CRAG 선별 후의 값이라 근거 수가 적다. 근거 정밀도(불필요한 근거 비율)는 이번에 재지 않았다.
- `vector` 기준선은 직업명 정확 일치 보강([Langfuse 디버깅 보고서](CareerGraph_Langfuse_디버깅_보고서.md) 사례 1) **이전** 코드다. 보강 후 일반 30문항의 벡터 정답 직업 재현율은 29/30 → **30/30**이다(`eval/search_modes/exact_name_fix.json`).

### 불일치 원인과 판단
1. **Multi-hop 30건: 기대 hybrid, 실제 graph.** 평가셋은 "공통 학과를 통해 두 직업을 연결한 뒤 능력·자격을 구분"하는 질문을 hybrid(업무 설명으로 직업 찾기 + 관계)로 정의한다. 그런데 이 질문들은 직업명·학과명이 질문에 이미 명시돼 있어 Jev 분류 기준("엔티티가 명시되고 관계만 요청하면 graph")에 정확히 해당한다. 위 3장에서 이 질문들은 **graph가 hybrid보다 정답 근거를 더 잘 찾았다**(재현율 0.867 vs 0.817, 근거 수 3.9 vs 10.8). 따라서 라우터가 틀린 것이 아니라 **평가셋의 기대값이 실제 질문 성격과 어긋난 것**으로 보인다. 팀 결정 필요: 평가셋 기대값을 graph로 고치거나, 라우터 기준을 바꾼다.
2. **근거부족 3건(EVAL100, 110, 120): 기대 vector, 실제 graph.** "…관련 학과 졸업생의 내년 취업률을 확정해 주세요"처럼 학과 관계를 언급해 graph로 갔다. 모두 보류·부분 답변으로 끝나 결과에는 영향이 없다.
3. **hybrid가 한 번도 선택되지 않았다.** 138문항 중 hybrid로 끝난 경우가 없다. 도구(`hybrid_search`)는 구현돼 있고 직접 질문하면 동작하지만("일기예보관의 업무와 관련 학과…" → hybrid), 평가셋에는 이를 고르게 할 "업무 설명으로 직업을 찾고 그 관계를 묻는" 질문이 없다.

### fallback과 재검색 기록

| 상황 | 건수 | 동작 |
|---|---:|---|
| 관계 검색이 빈 결과 → 직업 설명 벡터 검색으로 보충 | 3 (관계비교) | `search_node`의 fallback. 이후 `graph`로 재검색해 근거 확보 |
| CRAG 판정이 부족 → 검색어 재작성 후 재검색 | 40 | 한 번까지(`MAX_REWRITES=1`) |
| 재작성 뒤에도 일부만 확인 → 부분 답변 | 19 | 확인된 부분만 답하고 없는 항목을 밝힘 |
| 근거 0건 → 보류 | 5 | "현재 자료만으로는 답변을 확정하기 어렵습니다" |
| 검색 분류·도구 실패 → 오류 안내 | 0 (평가 중) | `search_routing_failed` / `search_unavailable` 오류로 끝나며 근거 부족과 구분. 별도 테스트로 확인 |
