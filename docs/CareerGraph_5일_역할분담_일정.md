# CareerGraph 5일 개발 일정과 역할 분담

> **최신 범위 결정 (2026-11-12) — 아래의 기존 설계보다 우선 적용**
>
> 이번 구현·인덱싱·검색·시연에서는 한국직업전망 **PDF 데이터와 PDF 매핑을 제외**한다. 아래 기존 내용 중 PDF 적재·인용·시연을 전제로 한 부분은 이전 설계 기록이며 현행 작업이 아니다. 기존 데이터 파일의 삭제를 뜻하지 않는다.
>
> 벡터 임베딩 대상은 커리어넷 `jobs.csv`의 **`work` 컬럼(직업 업무 설명)만**이다. 직업별 `work`를 단위로 사용하며 빈 값은 제외하고 건수를 기록한다. 문서와 사용자 질문은 같은 `text-embedding-3-small` 모델과 동일 차원으로 임베딩한다. 문서 벡터는 사전 생성하고 질문만 검색 시 임베딩한다. 직업명은 텍스트 문맥으로 포함할 수 있으나 임베딩할 설명 컬럼은 `work`로 한정한다.
>
> **벡터 검색 메타데이터는 `job_code`, `job_name`, 원본 `work` 텍스트 세 가지만 사용한다.** 그래프 조회는 `job_code`를 이용하며 학과·관련 자격·능력은 메타데이터에 중복 저장하지 않고 기존 Neo4j 관계를 사용한다. 벡터 자체와 저장소의 기술적 레코드 식별자는 메타데이터 세 항목과 구분한다. `source_locator`, PDF 페이지 등은 벡터 메타데이터에 추가하지 않는다.
>
> 이 범위에서는 업무 외 교육·전망 등의 설명이 벡터 검색 대상이 아니므로, 근거가 없는 질문은 확인 불가로 처리한다. 관련 자격을 필수 자격으로 단정하지 않는다. 기존 PDF 평가 질문과 시연 항목은 제외하거나 API 근거 질문으로 교체하고 정답·근거를 재검토한 뒤 평가한다. 다중 데이터 출처가 과제 필수 요건인지 강사에게 확인한다. 관계 근거의 출처 확인은 벡터 메타데이터와 별도로 원본 관계 데이터에서 수행한다.
>
> 이는 설계 변경이며 임베딩 생성, 데이터 삭제, Neo4j 적재 또는 배포가 완료됐다는 뜻은 아니다.

> 상태: 개발 전 실행 계획. 날짜는 팀의 실제 시작일에 맞춰 정한다. 아래 완료 기준은 목표이며 실제 달성을 의미하지 않는다.

## 1. 목표와 작업 범위

커리어넷 직업·학과·자격·능력 데이터와 검토된 한국직업전망 PDF 근거를 사용해, 출처와 그래프 경로를 제시하는 진로 탐색 GraphRAG를 구현한다. Streamlit Community Cloud, Neo4j Aura Free, LangGraph Supervisor와 역할별 에이전트, NeMo 입력·출력 가드레일, Langfuse 추적, RAGAS 평가를 포함한다.

현재 저장소의 `data/expanded_20261108/`에 그래프 데이터·검색 청크·평가 질문 초안이 있다. PDF는 기존에 검토된 연결만 사용하고, 관련 자격을 필수 자격으로 표현하지 않는다. 데이터 수량과 상태는 적재 시 다시 확인한다.

### 5일차 UI 작업 계획

- **첫 2~3시간 목표:** AI 코딩 도구로 질문 입력, 답변, 출처·관계 경로, 보류·오류 안내만 있는 단일 화면을 만들고 4일차에 고정한 백엔드 호출에 연결한다. 예상 시간이며 실제 소요는 달라질 수 있다.
- 이후 남은 시간은 Cloud 배포, 네 가지 대표 질문, 가드레일·출처 표시 검증, 수정과 리허설에 사용한다. 세 명이 각 담당 경계를 확인한다.
- 1일차의 Cloud 최소 기동은 의존성·연결 위험을 확인하기 위한 기술 시험이며, 실제 제품 UI 개발은 5일차에 진행한다. 1~4일차는 백엔드 실행 결과와 테스트로 확인한다.

### 매일 운영 방식

- 시작 15분: 전날 산출물, 오늘의 연결 지점, 막힌 점을 공유한다. 마감 전 30분: 브랜치 통합, 실제 질문 한 건 실행, 담당자와 다음 작업을 기록한다.
- 기능별 브랜치와 작은 PR을 사용한다. 담당자 외 한 명이 변경 내용과 시연 결과를 확인한다. 기존 데이터·팀원 파일은 확인 없이 덮어쓰지 않는다.
- 1일차에는 아래 최소 인터페이스를 합의하고 실제 구현과 함께 조정한다. 목 데이터로 각자 먼저 작업하되 통합 전 실제 데이터로 검증한다.

| 전달 지점 | 최소 전달 내용 | 담당 간 확인 |
|---|---|---|
| 적재 → 검색 | 노드·관계 스키마, 직업 식별자, 원본 필드·문서·페이지, 청크 ID, 적재·검증 결과 | 이승재 ↔ 오현탁 |
| 검색 → 검증 에이전트 | 질문, 검색 방식, 근거 ID·원문, API 필드 또는 PDF 페이지, 그래프 경로, 검색 실패 여부 | 오현탁 ↔ 송진명 |
| 에이전트·가드레일 → UI | 답변 또는 보류·차단·수정·오류 상태, 출처·경로, 안전한 안내 | 오현탁 ↔ 송진명, 이승재 출처 확인 |
| 평가 → 보고 | 질문 ID, 기대 답변·경로·원문 근거, 실제 결과, 평가 버전·오류 | 송진명 ↔ 이승재, 오현탁 확인 |

## 4. 일정 지연과 우선순위

1. **1일차 배포 적합성 실패:** 설치·연결 로그와 버전·담당자를 기록하고 2일차 오전에 재시험한다. NeMo가 계속 실행되지 않으면 강사에게 요구사항 충족 방법을 확인하고 미완료로 표시한다. 다른 필터로 바꿔 NeMo 완료라고 쓰지 않는다.
2. **Aura 벡터 인덱스·용량 문제:** 기초 설계의 사전 생성 벡터 인덱스 대안을 실제 플랫폼·메모리·재현성까지 확인한다. 그래프는 Aura를 유지한다. 해결 전에는 제한 사항을 기록한다.
3. **시간·비용 부족:** 먼저 직업·청크·평가 표본 수, 미검토 PDF 연결 확대, UI 꾸미기를 줄인다. 벡터·그래프 검색, Multi-hop, Supervisor, NeMo, 근거 검증·보류, Streamlit, Langfuse, RAGAS는 필수 목표로 유지하고, 실패 시 그 상태를 명시한다. 표본과 선정 기준을 보고한다.
4. **평가 시간 부족:** 검토된 소규모 질문부터 먼저 실행하고, 정답과 출처가 검토되지 않은 질문은 미검토로 남긴다. 보류·차단 질문은 일반 답변 점수와 따로 센다. 점수 향상을 가정하지 않는다.
5. **API 비용·키:** 호출량과 예산을 사전에 팀이 합의한다. 키는 로컬 비밀 설정과 Streamlit Secrets에서만 관리하고 Git, 문서, 스크린샷과 trace에 넣지 않는다.

## 5. 발표 전 공동 점검

- [ ] 배포 앱이 실제로 실행되고 데모 질문에 응답한다. 앱·DB 재시작 후에도 확인한다.
- [ ] 벡터 검색, 그래프 Multi-hop, Supervisor의 단계, NeMo 입력·출력 검사를 각각 확인한다.
- [ ] 근거 ID가 실제 API 원본 필드 또는 검토된 PDF 문서·페이지·구절에 연결된다.
- [ ] 근거 부족, 검사 차단·수정·오류를 구분하고 안전한 응답을 보여준다.
- [ ] Langfuse trace와 RAGAS 결과에 사용한 질문·데이터·모델·표본 수·실패를 기록한다.
- [ ] README의 설치·환경 변수 **이름**·적재·실행·평가 절차를 다른 팀원이 따라 해 본다.
- [ ] 데이터 이용 조건, 비용, 미완료 사항과 한계를 정리하고 시연을 리허설한다.
